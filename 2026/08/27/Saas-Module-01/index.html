Concept List

Two Development Methodologies

Many severe problems can be avoided with good methodology in software development. Some methodologies can even help other areas like civil engineering.

Learn from good practices, also learn from disasters.

Plan-and-Document Software Development

  • The core of this method is Planning and Detailed Documentation. The whole lifecycle relies on careful, up-front planning.
  • It works, but have many downsides, leading to many failures.

Agile Software Development

  • whose core is Prototypes. TODO: FIX THIS!!!
  • continuously incrementally refine the prototypes.
  • respond better to change, and enable developers to get feedback on time, and works well with smaller teams.
  • Each iteration takes about 1-4 weeks.
  • doesn’t work well with very large software and hardware.
  • Developers themselves is responsible for Software Quality, instead of QA Team.

SaaS: What, Why, and How

Software as a Product (SaaP)

  • user install/deploy sw on own device

Mobile Devices as Backgroud

  • Mobile Devices account for the majority of visits to websites.
  • SaaS is suitable for “Mobile-first” apps.
  • Responsive Web Design Automatically adapt to different screen sizes

Software as a Service (SaaS)

  • software deployed on internet servers
  • accessible to millons of users.
  • eaiser to upgrade and evolves, only one copy is deployed

Cloud Computing

  • supplies dependable and scalable computation
  • supplies storage for Saas with Warehouse Scale Computers
    • contains as much as 100k servers

Synergy (协同作用) of:

  • Agile Software Development
  • Software as a Service
  • Cloud Computing

Plan-and-Document: From Software Development to Software Engineering

Background and Motivation

Background:

  • unpredictability of software development
  • many engineering disasters in late 1960s

“Software Engineering” was coined:

  • How: bring in engineering Discipline and Methods
    • extensive documentation
    • IEEE/ANSI standard 830/1993
  • Goal: make development more predictable in
    • quality, cost, time for development

Required Plan and Document for the project

  • Requirements & Designs
  • User manuals
  • Test instructions
  • Project Plans
  • Change Logs

Waterfall: Early Versions

Process/Lifecycle

  • Requirements Analysis and Specification
  • Architectural Design
  • Implementation and Integration
  • Verification
  • Operation and Maintenance

Time Schedule

  • First Release: Years
  • Maintanance & Update: 6-18 months
    • Go through the same lifecycle

Pros:

  • work well with well-specified tasks
  • needs and requirements are clear

Cons:

  • fails when the customers frequently change their minds

Spiral Model: Improvement with Prototypes

Background

  • Given these downsides, people found that it is easier for customers to understand what they want once they see a prototype.
  • This led to Spiral Model, which is Prototypes with the Waterfall Model.
  • It iterate through a sequence of four pahses, each resulting in a prototype, which is a refinement of a previous one.

Process/Lifecycle

  • Determine Objectives and Constraints of this Iteration.
  • Evaluate Alternatives and Identify and Resolve risks.
  • Develop and Verify the Prototype for This Iteration.
  • Plan the Next Iteration.
    • documents: developed across the iterations; evolve with the project, like code.

Pros

  • allow each iteration to involve the customer before the product is completed
  • reducing the chance of misunderstandings.

Cons

  • each Iteration still takes 6-24 months long
  • still a high chance for customers to change their mind in such a long time.

Other Variations

Rational Unified Process (RUP)

Combines features of both Waterfall and Spiral, more allied to business issues than to technical issues.

  • Inception: makes the business case for the software and scopes the project to set the schedules and budget, which is used to judge progress and justify expenditures, and initial assessment of risks to schedule and budget.
  • Elaboration: works with stakeholders to identify use cases, designs a software architecture, seets the development plan, builds an initial prototype.
  • Construction: codes and tests the product, resulting in the first external release.
  • Transition: moves the product from development to production in the real environment, including customer acceptance testing and user traning.

Each phase involves iteration. A phase can has multiple iterations. For example:

  • 1 Inception Phase Iteration
  • 2 Elaboration Phase Iteration
  • 4 Construction Phase Iteration
  • 2 Transition Phase Iteration

A project could also iterate across all four phases repeatedly.

RUP also identifies six Engineering Disciplines or Workflows, which are more static than the phases.

  • Business Modelling
  • Requirements
  • Analysis and Design
  • Implementation
  • Test
  • Deployment

Summary

Waterfall Lifecycle

  • much of the design in advance
  • complete each phase before going on to the next one.

Spiral Lifecycle

  • iterates through all the development phases
  • produces prototypes

Rational Unified Process Lifecycle

  • includes phases, iterations, prototypes
  • identifying people skills for the project.

All rely on careful planning and documentation. All measure progress against a plan.

P&D Processes brought discipline to software development, but many projects still failed.

Elaboration: SEI Compability Maturity Model (CMM)

Evaluates organzations’ software development processes based on Plan-and-Document methodologies so that the process can be improved.

Five levels of software practice

  • Initial or Chaotic: undocumented/ad hoc/unstable software development
  • Repeatable: not following rigorous discipline, but someprocesses repeatable with consistent result.
  • Defined: Defined and documented standard processes that improve over time.
  • Managed: Management can control software development using process metrics, adapting the process to different projects successfully.
  • Optimizing: Part of the management process is delibereate quantitative optimization of the development process

Some consider level 2 as Agile.

The Agile Manifesto

Background

Many P&D projects failed to meet the time/schedule and budgets, and many are cancelledor abandoned.

We are uncovering better ways of developing software by doing it and helping others do it. Through this work we have come to value:

Agile Manifesto is a lighter-weight software lifecycle.

  • Individuals and Interactions over processes and tools
  • Working Software over comprehensive documentation
  • Customer Collaboration over contract negotiation
  • Responding to Change over following a plan

That is, while there is value in the items on the right, we value the items on the left more.

Principles

  1. Test-Driven Development (TDD)

Agile emphasizes writing tests before writing the code to reduce mistakes.

  1. User Stories

Reach agreement and validate customer requirements.

  1. Velocity

Measures project progress.

Software Lifetimes

Agile software lifecycle

  • is very quick, new versions are available every week or two, even everyday.
  • de-emphasizes planning, documentation, and binding specifications.

On the one hand, it is welcomed, because it is more friendly to developers. But on the other hand it is controversial and questioned, because it seems less predictable.

However, more researches showed that Agile indeed work very well.

Variants and Tools

Like P&D, Agile is also a family of methodologies.

Extreme Programming (XP)

  • 1-2 week iterations
  • behavior driven design
  • test-driven development
  • pair programming

Scrum

  • 2-4 week iterations called Sprints
  • self-organizing teams: regroup to plan the next sprint

Also, to overcome its obstacles, Agile implements many useful tools and approaches.

Kanban Approach

  • treats software development as a pipeline
  • fixed roles of team membet
  • balance the number of team members to reduce bottleneck
  • a wall of cards illustrating the state of tasks
  • hybrid lifecycles that try to combine the best of two worlds, ScrumBan

Summary

Agile was born from small teams and small projects, but not all projects are small.

Agile works with customers to

  • continuously add features to prototypes until the customer is satisfied.
  • allow customers to change what they want as project develops.

Documentation is primarily through

  • User Stories
  • Test Cases

Agile does not measure progress against a predefined plan. Progress is gauged by recording velocity, the rate that a project commpletes features.

Testing: Assures Software Quality

Quality of any product: Fitness for use.

  • provide business value for both customer and the manufacturer.

Quality for Software:

  • satisfying the customer’s needs
    • easy to use, correctness, does not crash, etc.
  • being easy for developers to debug and enhance.

Quality Assurance (QA): comes from manufacturing

  • process and standards that lead to manufacture of high-quality products
  • introduction of manufacturing processes that improve quality

Software QA

  • ensuring products under development have high quality
  • creating processes and standards in an org that lead to high quality software

Distinguishing Verification and Validation

Verification

  • Did you build the thing right?
  • Did you meet the specification
  • More important in hardware.

Validation

  • Did you build the right thing?
  • I sthis what the customer wants?
  • Is the specification correct?
  • More important in software.

Software prototypes in Agile help with Validation rather than verification to keep up with customers’ minds.

Testing: Verify and Validate

The main approach to both Verification and Validation is Testing.

Motivation: the earlier developers find mistakes, the cheaper it is to repair them.

However, the combinations of inputs has a vast number. To reduce its space, we do different testing in different phases of software development.

  • Unit Testing: single procedure or method, within a class
  • Module Testing: across individual units, involving different classes
  • Integration Testing: interface between units have consistent assumptions and communicates correctly
  • System Testing / Acceptance testing: integrated program meets its spec.

There is also an alternative to testing: Formal Methods.

One way to do it: XP

Write tests before writing code. Then write minimal code to pass the tests. So, the code is always tested, and reduce the chances of writing discarded code.

XP splits the test-first philosophy into 2 parts:

System, Acceptance, Integration Tests:

  • uses Behavior-Driven Design (BDD)

Unit, Module Tests

  • uses Test-Driven Development (TDD)

Summary

Testing reduces the risk of errors in designs.

Helps verify and validate

Tests are divided to avoid exhausting.

Agile do tests before code, and use BDD and TDD.

Productivity of Development: Conciseness, Synthesis, Reuse and Tools

Moore’s Law -> Bigger Apps -> Higher Productivity Requirements

Four fundamental mechinisms to improve productivity

  • Clarity via Conciseness
  • Synthesis
  • Reuse
  • Automation via Tools

Clarity via Conciseness

if programs are easier to understand, they will have fewer bugs and will be easier to maintain.

One Way: Program Language

Another Way: Higher Level Abstraction

Assembly -> High Level Languages
Deligate more to Compilers and Runtime
C/C++ -> Java -> Ruby, Python

Reflection is an example of higher level abstraction, allowing programs to observe themselves.

Higher order functions, allows higher-level behaviors to be reused, by passing functions as arguments to other functions.

Synthesis

Generate Code automatically rather than create manually.

Often used in hardware design.
Classic Synthesis software: Bit Blit.

Rails framework makes extensive use of the Ruby language’s facilities for metaprogramming, which allows Ruby programs to automatically synthesize code at runtime.

Reuse

Reusing portions from past designs. It is easier to make changes than building from scratch.

Ways to reuse:

  • Standardized Libraries
  • Object Oriencted Programming (OOP)
  • Design Patterns
  • Language Support
    • Dynamic Typing
    • Mix-ins
    • Funtional Programming

Reuse doesn’t mean copying and pasting code so that it appears everywhere. It is called repetition, which is bad.

The guidelines for reuse:

Every piece of knowledge must have a single, unabiguous, authoritative reprensation within a system.

Which is captured in the motto and acronym: Don’t Repeat Yourself (DRY)

Automation

Replacing tedious manual tasks with tools to save time, improve accuracy or both.

Compilers, Interpreters are tools that raise abstracction levels and generate codes.

Makefiles, Version Control Systems are more used to automate tedious tasks.

Common Tradeoff:

  • Time used to learn and choose tools
    • Dependability of the tool
    • Quality of the user experience
  • Time saved in applying it.

New tools usually make our lives better.

Example tools

  • Cucumber: automate turning user stories into acceptance tests
  • Pivotal Tracker: automatically measures Velocity
  • RSpec: automate the unit testing process.

Summary

Moore’s Law inspired engineers to improve productivity.

Conciseness

  • compact syntax
  • raising level of abstraction
  • reflection, higher-order functions

  • DRY

SaaS and Service Oriented Architecture

Background: Web is gaining larger audiences. This inspires a new idea: rather than relying on users’ devices to install software, why not run software centrally on servers?

This new model is called Software as a Service (SaaS)

Advantages

  • Customers don’t need to worry about their own hardwares, as long as it can run web browser.
  • Customers don’t need to worry about data backup.
  • A group of users can interact with the same data.
  • Centralizing makses more sense in hadling large, frequently updated data..
  • Only single copy of server software is deployed, no need to care about compatibility on different devices. (it requires compatibility of web browsers, but it is much easier)
  • Developers have full control to update, without changing Application Program Interfaces (API)
  • Encourages competition among SaaS companies.

Frameworks Helps with SaaS

  • Active Server Pages (ASP.NET) for C#, VB.NET
  • Enterprise Java Beans (EJB) for Java
  • JavaServer Pages (JSP) for Java
  • Spring for Java
  • Rails for Ruby
  • Django for Python
  • Zend for PHP
  • Sinatra for Ruby

Disadvantage:

  • Software libraries for SaaP

Mitigation:

  • Service-Oriented Architecture (SOA), allow SaaS services call other services built and maintained by others.
  • It became Microservices

Summary

attractive to both customers and providers.

  • easier for customer to use the service, due to the use of the universal client: Web Browser.
  • easier for provider to deliver and improve, due to centralized deployment.
  • works well with Agile Software Development Process

Cloud Computing: Deploy SaaS

Demand of SaaS:

  • Communication: allow any customer to interact with the service
    • Resolved easily by broadband to home.
  • Scalability in the Central Facility: deal with the fluctuations in demand during popular times
  • Availability in both Service and Communication Vehicle: 24x7 available, 99.999% (five nines) rule, 5min of downtime per year.

From Big Iron to Datacenter

Early web services were deployed on expensive large-scale machines. They are more reliable and easier to operate.

However, another approach has taken over the industry: Collections of commodity small-scale computers, connected by commodity Ethernet switches. Known as Clusters.

The Clusters has several advantages:

  • Much more scalable due to their reliance on Ethernet. It can contain 100k or more computers now.
  • Virtual Machines can simplify operations to carefully controlled and selected hardwares.
    • imitate with low overhead.
  • even more efficient way is OS-Level Virtualization (Docker is an example)
  • Lower Costs than for “big iron”, by a factor of 20.
  • Though less reliable, but more dependable by affordable redundancy in multiple datacenters.

Cloud Services

Some big datacenter owner finds that their cost per capita is sustainably lower than other smaller datacenter owner.

So, by sharing giant datacenters, untility can be increased, and benefits are made for both owner and customer.

The result is called Public Cloud Services / Utility Computing / Cloud Computing.

It offers computing, storage and communication at pennies per hour, with no additional cost for scale. The cost is the same when using 1 computer for 1000 hours as when using 1000 computers for 1 hour.

Summary

The engineering SaaS for Cloud Computing is radically different from engineering SaaP for PCs and Servers.

The Internet supplies the communiation for SaaS

Cloud Computing provides the scalable and dependable hardware computation and storage for SaaS.

Cloud computing consists of clusters of commodity servers connected by local area networks switches.
A software layer providing sufficient redundancy to make it cost-effective while dependable.

These large clusters are called Warehouse Scale Computers, and offer economies of scale.

Cloud Computing providers offer hardware infra as low-cost utility computing that anyone can use.

Browsers and Mobile

Success of Web wipe out many SaaP apps, browser has become universal client.

The user interface of site is described by the Hypertext Markup Language (HTML). Then, JavaScript entered to enrich the interactive experience of Web Pages.

Markup Language: combines text with markup (annotations about the text’s structure) in a way that makes it easy to syntactically distinguish the two.

HTML 5 is one type of document that can be expressed in Extensible Markup Language (XML). XML can be used to represent data and to describe other markup languages.

Appearance and CSS

Later, the Appearance information in HTML is separated from the Logical Structure.

Logical Structure

  • logical component of page
  • div: group together logically related elements

Appearance

  • basic typography: fonts, colors
  • layout of elements on the page

Cascading Style Sheets (CSS) is used to separate struycture and appearance. It associate visual rendering information with HTML elements.

One key concept of CSS is Selector: an expression that matches on or more HTML elements in a document. Selectors are also used as a mechanismm in JavaScript to create interactive Web Pages.

One of the most widely used approach is to associate the selector with an element’s class attr

Mechanism of CSS to style HTML

When browser loads the page, it looks for one or more link elements, which should be children of the HTML document’s head element, that specify stylesheets to be used in conjuction with this document. In this case, the link’s href refers to the main stylesheet of Bootstrap CSS.

The browser loads each referenced CSS stylesheet. A stylesheet contains a set of selectors and for each selector, a set of rules for how to display emelements mathcing that selector. These rules can specify typography, layout on the page, colors and more.

When displaying the page, the browser matches up the CSS rules with the matching elements on each displayed page. In this example, Bootstrap provides basic style rules for each element type, and the class attr on various elements are there to match particular CSS selectors in Bootstrap that further “tweak” the formatting of specific page elements.

Use Frameworks

Good visual design of CSS requires skills. We can use the stylesheets designed by professionals and use CSS frameworks or even front-end frameworks.

A good CSS framework provides at least four main benefits:

  • A set of high-level compoents that combinemultiple HTML elements into a logical unit
  • A grid metaphor for specifying the layout of components on a page. Bootstrap divide the page into 12 cols.
  • Responsive behavior on a variety of display sizes.
  • Support for accessibility for users with disabilities.

These frameworks have become particularly important with the takeover of mobile devices.

Comparing different apps

Mobile First / Responsive Web Apps

Advantages

  • Use same languages, tools, frameworks
  • Portable across devices, no need to develop multiple versions
  • User don’t need to install updates
  • Can be offline
  • Icon placement on user’s home screen

Disadvantages

Advantages

  • Can be listed in app stores

Disadvantages

  • Additional frameworks to package app for distribution

Platform apps

Advantages

  • Best performace
  • Can be listed in app stores

Disadvantages

  • rely on users to install updates
  • Support multiple platforms requires maintaining multiple codebases

HTML consists of hierarchically nested collection of lelemnts. Each begins with a tag and may have optional attributes. Elements describe the logical structure of the docuemnt.

Cascading Style Sheets (CSS) is a stylesheet language describing visual attributes of elements on a Web Page. Associates sets of visual properites with selectors.

CSS are separated from HTML documents.

Mobile devices now account for the majority of visits to SaaS apps.

Use framework or use platform specifc apps to build apps. Both have pros and cons.

Beautiful v.s. Legacy Code

Background

Software is expected to grow and evolve more compared to hardware, because they can be easily upgraded over time.

The drivers of Software Evolution are not only fixing faults, but also

  • adding new features
  • adjust to changing business requirements
  • improving performance
  • adapt to a changed environment

Older code is hard to maintain because of its lower Abstraction Level.

However, Software enigneers would still hope their works can be long lasting.

Legacy Code

The term Legacy Code refers to software that despite its old age, continues to be used because it meets customers’ needs.

60% of software maintenance costs are for adding new functionality to legacy software, while only 17% fixing bugs.

Legacy Software is Successful Software.

Legacy v.s. Beautiful

The word “Legacy” has a negative connotation, and it indicates that the code is difficult to evolve because it has an inelegant design or uses antiquated tech.

We use the term “Beautiful Code” to indicate long-lasting code that is easy to evolve instead.

Though Legacy is not as good as Beautiful, but it is not the worst. The worst case is Unexpectedly Short-Lived Code that is soon discarded because it is useless.

Why are we learning this?

We want to reduce the effort to build by finding existing code that we can reuse.

It is also beneficial to write code that can be easily enhanced by successors.

In Agile, we need to revise code continuously to improve the design and add functionality. Practice with legacy code helps this.

Summary

While hardware should be finalized for manufacture, Successful software can live long and is expected to eveolve and improve.

Our goal is to increase the chances of producing beautiful code.
