Rails as a Model-View-Controller Framework

Concepts

Good software systems reflect organization at multiple levels of granularity, often based on identifiable architectural patterns.

Rails: Server Side of C/S Arch, includes another architectural pattern MVC

  • Models are stored in a relational database using the Active Record design pattern.
  • Views use the Template View pattern to create HTML or JSON representations of resources.
  • Controllers, follow Representational State Transfer, where each comtroller action describes a single self-contained operation on one resource.

Rails can be used to build both

  • SaaS apps designed for browser
  • Microservices adapted to work in a service oriented archiecture

Rails uses Ruby’s features of Metaprogramming and introspection to provide convention over configurration.

  • Following certain conventions, so configuration can be avoided.
  • Makes apps smaller and simpler to understand and maintain.

Debugging SaaS requires understanding

  • different places where someting could go wrong in the flow
  • how to surface that information to the developer.

MVC Architecture

All well-written andnontriially-sized applications reflect some macroarchitectural organization, and can be thought of as ensembles of large communicating subsystems.

Model-View-Controller (MVC) is such architectural pattern.

An application organized according to MVC consists of three main types of code

  • Models: data manipulated b the application
    • how to store, operate,change
    • have a model for each tpe of entity
  • Views: presented to user, managge user interactable informaiton
    • serve as the interface between the user and the data
    • Rails view is a special case called template view: staticmarkup interspersed with variable substitution, processed by a generic logic engine.
  • Controller: mediate the interaction in both directions
    • a specific controller action is invoked when user interacts with a view.
    • each oltroller corresponds to one model.
    • each controller action is handled by a particular Ruby method within that controller.

Alternatives

  • Model-View-Presenter: an embellishment of MVP
  • Model-View-ViewModel: provides two-way interaction between the model and the view so that pdates to the view automatically occur in the modal
    • while MVC, the focus is on reflecting model changes in the view.

MVC with Rails

  • Rails is designed to support MVC apps, provides powerful base classes for MVC.
  • Each Rails Model is a resource type whose instances are rows ina particular table of a Relational Database. Data in DB are exposed to ruby via a design pattern known as Active Record.
  • Rails app can be viewed as a collection of restful resources, each has its own M, C and a set of Vs. Resources may or may not have relationships to each other. Foreigh keys in the database capture such relationships
  • Rails is a server-side framework, provides a flexible way to map an HTTP route to code.
  • Rails is designed for apps whose client was a Web Browser, and its view system is designed aaround generating HTML page.
  • Rails embodies strong opimions about mechanical details for app implementation. It uses convention over configuration to save you from work.

Summary

MVC is one of a family of patterns for structuring interactive applications.

Models: business logic
View: present information
Controller, Mediate interaction

Every user action that can be performed on a web page is eventually handled by some controller acion, which consult the model and return a view.

Rails heavily uses convention over configuration.

Models: Databses and Active Record

Databases

For many SaaS apps, there are two key requirements for storing and manipulating persistent data

  1. Structures: The app must be able to store different types of data items, or entities.
    • all instances of a particular type of entity share a common set of attributes
  2. Relationships: The app must be able to express relationships among different kinds of entities

Relational Database Management Systema (RDBMS) emerged as elegant structured-storage systems.

  • stores a collection of tables

Resources in Rails

In Rails, data is considered as a set of resources stored in a relational database.

What is the correspondence between

  • how resource is stored in the database?
  • how it is represented in the framework/language?

What software mechanisms mediate between those two representations? What programmig abstractions do those mechanisms expose?

Rails is Active Record Architectural Pattern

  • Rails Model is a class backed by a specific table of an RDBMS.
  • An instance of the class corresponds to a single row in that table. The combination of table name and ‘id’ uniquely identifies a model instance.
  • The model has built-in CRUD behaviors that directly operate on the database.

Active Record as Abstraction

Many other SaaS frameworks provides a connection to a DBMS as an abstraction.

Active Record gives each model the knowledge of how to CRUD instances of itself.

  • logics talking to the database, serialization and deserialization attributes are implicitly included in eah model

This is accomplished with : ActiveRecord::Base

  • Inherit from this base class provides all the necessary mach9inary to connect to the model to the database.
  • Create, Read: Class methods defined on the collection of model istances as a whole
  • Update, Delete: Instance methods define on a specific model instance

Conventions

  • app/models contains one ruby code file per model.
  • file name is determined by converting class name to lower_snake_case.
  • the databse table name is determined by the class name to lower_snake_case and pluralizing it.
    • class name: Movie -> file name: app/models/movie.rb -> table name: movies
  • the attributes of model and types are inferred from the names and types of the table’s columns
  • the model automatically has class methods new, create
    • expecting a hash of arguments
    • whose keys match those attribute names
    • whose values supply the attribute values for a instance to be created
      • in memory (new)
      • immediately perissited in the database (create)

Migration

When a new Rails app is created from scratch, the automatically-generated file config/database.yml specifies how to connect to the databse.

  • default: SQLite
  • can be modified to MySQL and Postgres

We must create the table in the database ourselves with Migrations

  • migration is a ruby script describing a set of changes to tmake to the database schema.
  • we use these scripts, instead of directly using SQL statements.

Rails defines 3 environments

  • development: when coding
  • test: only when running automated tests
  • production: the live app containing real customer data

They are 3 separate databases, but their schemata should be kept in sync. So it is more reasonable to write a single migration script.

Rails will create a Ruby file whose name consists of this name plus a timestamp. The file defines a migration class with yyour specified name that descends form ActiveRecord::Migration and has an empty change instance method.

We need to fill in that method with the desired schema changes. Then, run rake db:migrate, which invokes the tool rake to run the task.

We don’t need to specify the filename of migration, Rails tracks which migration have been applied to which environment’s databases.

Summary

Rails implementation of ActiveRecord uses convention over configuration to infer database table names from the names of model classes, and to infer the names and types of the columns associated with a given kind of model

Basic Activercord support focuses on the CRUD actions

Every model instance saved in the database recceives an ID number unique within its table called the primary key, whose attribute name is id and which is never “recycles”. The combination of table name and id uniquely identifies a model instance stored in the database, and is therefore how objects are usually referenced in RESTful routes

changing the database schema including creating the tables needed by your models is accomplished by creating and running migrations. Rails itself tracks which migrations have been applied in each of the three environments: development, production, testing

If we run the code directly without migration, error will occur because the model cannot find its corresponding database table.

Overriding convention over configuration

Though Convention over Configuration is great, but sometimes we need to override it.

  • integrating rails app with a non-rails legacy app
  • friedlier attr names than those given by taking the names of the table columns.

All the defaults can be overriden.

Routes, Controllers, Views

Routes

The app will receive a request in the form of an HTTP route. So the app should determine which code in the app should be invoked to handle that route.

Rails provides a flexible routing subsystem that maps routes to specific Ruby methods in each controller: config/routes.rb

Though we can define any routes we like, but we would like to follow the RESTful conventions

For each of the resources, we can define 7 different kinds of routes.

  • CRUDI has only 5, why 7?
    • for we not only need to provide information, but also need to collect information from user with forms.
    • new, edit collects information
    • create, update operates on the resource
  • How does browsers generate requrests other than GET and POST?
    • Browswers only implement GET and POST.
    • Rails annotate the fomrs, so it allows the web browser to use POST for requests, and rails internally changes the request methods, so it appears that the browser generates PUT or DELETE
  • How are parameters in the route URI made availablel to the controller action
    • the routing subsystem prepares a hash called params[] that is made available to thecontroller.
    • we can use rake routes to inspect the routes and params. then, we can use params[:id] to get the parameters.
  • What are route helper methods?
    • by convention over configuration, the route URIs will match the resource name, but we can override this behavior.
    • we may want to have routes built around film rather than movie.
    • however, any view in the app that references the movie route URIs would have to be changed to film.
    • helpers can solve these problems: they decouple what the route does, from the actual route URI.

Controller

Controller methods/actions handles RESTful operation.

Route: resources 'movies'

  • expect controllers/movies_controller.rb
  • which defines MovieController < ApplicationController
  • which defines instance methods: index, new, create, show, edit, update, destroy

Each of conroller actions follows a similar pattern

  1. Collect the informaiton including parameters, etc.
  2. Determine which ActiveRecord operations are necessary.
  3. Set instance variables for any informaiton that will need to be displayed in the view.
  4. Render a view that will be returned as the result of the overall request.
    • views/<model-name>/<action>.html.erb

View Templates are not legal HTML!

  • lack an HTML DOCTYPE, including <html> element and its children <head> and <body>

Rails Design

To make the coding easier, the designer of rails violates OOP orthodoxy, making some instance variables of one class (MoviesController) be accessible to an object of a completely different class (ActionView::Base).

Actually, rails creates an instance of ActionView::Base to handle rendering the view, and then uses Ruby’s metaprogramming facilities to “copy” all of the controller’s instance variables into that new object.

  • The controller code is in MoviesController in app/controllers/movies_controller.rb
  • Your class inherits from ApplicationController in app/controllers/application_controller.rb.
  • This class contains controller behaviors common to multiple controllers, and this class inherits from ActionController::Base

Summary

Rials provides various helper methods that take advantage of the RESTful route URIs, including link_to for generating HTML links whose URIs refer to RESTful actions

Convention over configuration is used to determine the file names for controllers and views corresponding to a given model. If the RESTful route helpers are used, as in resources :movies, convention over configuration also maps RESTful action names to controller action names

Although the most common way to finish a controller action is to render the view corresponding to that action, for some actions such as create it’s more helpful to send the user back to a different view. Using redirect_to replaces the default view rendering with a redirection to a different action

Although redirection triggers the browser to start a brand-new HTTP request, the flash can be used to save a small amount of information that will be made available ot that new request, for example, to display useful information to the user regarding the redirect

Metaprogramming in Rails

In Active Record, getter and setter instance methods for ActiveRecord models are defined at runtime by inspecting hte database schema.

In the routing subsystem, route helpers such as new_movie+path are defined at rruntime based on the contents of config/routes.rb

Controller methods automatically knowing how to locate the default view to render is also an example of convention over configuration, there’s no new code that needs to be generated at runtime to support it.

Example

Forms

We have already seen views that display data to the user, but not views that collect data from the user. The simplest mechanism for doing so is HTML forms.

How do we display a fill-in form to the user?

How is the information filled in by the user made available to the controller asction, so that it can be used in a create or update ActiveRecord call

Tag Helper

  • rails by default defines a new action for this purpose, and can be found in a view app/views/moviesnew.html.erb
  • since a scenarrio that a form whose fields represent attributes of an ActiveRecord model object is so common, rails streamlines the precess by using for tag helper methods.
  • these helper methods generate HTML form tags whose names follow particular conventions that make them easy to parse by the controller actions.

The form_tag helper takes two arguments

  • the URI to which the form should submit. the RESTful route helper is used to generate that URI.
  • a hash of optional arguments, one of which may be the HTTP method that should be used to submit the form.
    • POST is the default, GET is acceptable.
    • If you use DELETE, PATCH, PUT, the browser would still use POST, but the app would interpret as the specified method.

Not all input field types are supported by the form tag helpers (like date), and in some cases you need to generate forms whose field don’t necessarily correspond to the attributes of some ActiveRecord object.

tag hepers are not required, but since it is a common procedure, using them saves your work and results in less code.

Parsing the user submission powered by rails

Recall that Movie.create call takes a hash of attribute names and values to create a new movie instance in the database.

The reason to use frm tag helpers is:

  • the form fields created by the form tag helpers have names of the form movie[title], movie[rating], and so on.
  • hence, the value of params['movie'] is exactly the hash of movie attribute names and values.
  • as a result, we can directly pass along using Movie.create!(params['movie'])

This is how a framework simplify the mechanical work of making the models, views, and controllers in a SaaS app work smoothly together.

Security

“Mass assignment” of a whole set of attributes as occurs when we pass the hash params['movie'] to an ActiveRecord call, is a mechanism that could be used by a malicious attacker, to set model attributes that shouldn’t be changable by regular users.

Rails requires us to declare in the controller which elements of params are required to be present for a given action, and critically, which elements are permitted to be asigned to model attributes.

This mechanism follows the principle of least privilege in computer security.

flash and session

What should we display when the create action completes?

Convention over configuration suggest a view app/view/movies/create.html.erb that simply confims the movie was created, and provides a link or other mechanism to go back to the list of movies.

But there is no nead to have a separate view just to do that.

One alternative is: streamline the user experience by just redirectly the user to the newly-updated list of all movies, but arrange to display a confirmation message on the page.

The DRY way to proceed is to have the controller action issue an HTTP redirect, telling the web browser to start an entirely new request for the Index action.

  • This approach has a small problem: HTTP is statelens, in the new request, all of the variables associated with the prior create request are gone.
  • That prevent us to display the confirmation message.

To address this scenario, the flash[] is a sepcial object available in a controller tha quacks like a hash, but whose contensts persiste only from the current request to the next.

  • we can only pass information to the very next action.
  • conventions:
    • flash[:notice] is used for informational messages.
    • flash[:alert] is used for messages about things going wrong.
  • using the flash conjunction with a redirect is a common combination, so the redirect_to method provide a special syntax for it.
    • redirect_to movies_path, :notice => “#{@movie.title} deleted.”

Actually, the flash is a special case of the more general session[] object, whose contents persiste “foreverl” across requests from the same browser (until cleared manually)

Summary

When creating a form you specify the controller action that will receive the form submission by passing form_tag the appropriate RESTful URI and HTTP method (as displayed by rake routes).

It’s convenient, but not required, to use RESTful URI helpers like movies_path and edit_movie_path rather than creating the URIs manually.

When the form is submitted, the controller action can inspect params[], whose keys are the form field names and hose values are the user-supplied contents of the field.

If you use Rails from helpers, the field names are chose such that params[:<model>] is a hash whose keys and values are the user-supplied values ofr an instance of “model”.

When creating or updating a model object, for user friendliness, it’s common to simply redirect_to a view such as index, rather than redering a dedicated view.

When finishing a controller action using a redirect, flash[:notice] or flash[:alert] canbe set to a message that will persist until the next request.

It is conventional to modify the applicaiton layout to display such messages, so they get displayed no matter where the redirect points.

Every conrtrollerr action either render a view or perform a redirect. Because HTTP is a request-reply protocol, every action must generate a reply. Also, we can only have one reply, which means it makes no sense to have both a render and a redirect.

Debugging: When Things Go Wrong

Debugging is an annoying but invaluable skill.

The sophistication of today’s software stacks makes it highly productive but with so many “moving parts”.

It also means that things inevitably go wrong, especially when learning new languages and tools.

Error happen because mistyping, a change in the environment or configuration, etc.

Two fundamental suggestions for debug

The best way to debug is to stop a bug in its tracks and fix it before it manifests.

Two suggestions:

  1. use good tools including a text editorthat supports automatic indentation and syntax highliting.
    • helps avoid syntax errors.
  2. use good colleagues. by always pair programming, we may save a huge amounts of time, because the partner can catch a silly bug before it became a work stopper.
    • even explaining your code to a pet helps.

TIDE

Debuggin gusually involves a gradient of activities:

  • Trace the source of the error as closely as possible by really examing the error mesages and log files closely.
  • Instrument the code near the error, such as by inserting statemtns to print intermediate values of variables, to see where things go off the rails.
  • Debug interactively using the facilities provided in your language or framework, suchas byebug for Ruby.
  • Explore question boards such as StackOverflow for similar bugs, and if all else fails, post a question there and ask for help

Summary

Use a language-aware editor with syntax highlighting and automatic indentation to help find syntax errors.

Instrument app by inserrting the output of debug or inspect into views, or by making htem the argument of raise, which will cause a runtime exception that will display a message as a web page.

To debug using the interactive debugger, make sure you app’s Gemfile includes byebug and place the statement byebug at the point in your code where you want to break.

Fallacies and Pitfalls.

Pitfall: Bulky controller actions or views.

Do not let logic code creep into views or violating MVC.

Overstuffing the session[] hash

the session is packed into a cookie, which the HTTP specification limits to 4 KB.

bulky sessions are a warning that your app’s action aren’t self-contained and therefore probably not RESTful, and may be difficult to use as part of a SOA.

Adopting a framework without a good reason.

Software breeds complexity.

The more numerous and complex the libraries on which your app relies

  • the more you’ll have to learn to write the app properly;
  • the more resource-intensive the app will run
  • the harder it will be to maintain
  • the more exposure surface it will have for being attacked.

Use the simplest framework that will solve most of your problems.

The answer to the question “Should my app use framework X” should be NO by default, unless you can come up with good technical reasons why it should.
