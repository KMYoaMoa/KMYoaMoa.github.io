SaaS Application Architecture: Microservices, APIs and REST

Web’s Client-Server Architecture

Design Pattern Basics

C/S is a type of Design Pattern:

  • a reusable structure, behavior, strategym technique
  • captures a proven solution to a collection of similar problems
  • by separating the things that change from those that stay the same.

C/S Description

SaaS ased on web protocals is widely deployed as C/S Architecture

  • SaaS Client
    • Make one or more request to SaaS Server
    • Ask server for information, allow user to interact with the information
    • Mobile app, Browser, etc.
    • Clients on different platforms can access to the same server.
  • SaaS Server
    • Efficiently serving large numbers of clients simultaneously
    • Typically a collection o computers running multiple different software components.
    • The way for deployment depends on hosting environment and the user scale.
    • Users are unaware of server’s deployment topology.

Motivation For dinstinguishing C/S:

  • allow different type of programs to be specialized to its task.

Alternative for Webapp: Peer-to-peer architecture

BitTorrent: Every participant is both client and server, participant ask information from each other.

Harder to specialize the program to do either job well. But it is useful when the client machines are much cheaper than server machines.

However, since today’s mobile devices are becoming more and more powerful, the C and S are both very complex, but in different ways.

The history of web

1960: Sabre, Airline reservation system

  • Custom FM-based protocal, over leased tel lines

1971: FTP, File Transfer Protocol

  • ASCII-based FTP protocal over TCP/IP

1983: Novell NetWare, allow PCs to share files on a server

  • Custom protocals, PC compatible

1984: POP, Post Office Protocal, allow separation of email clients from servers

  • ASCII-based POP protocal over TCP/IP
  • largely superseded by IMAP

1990: World Wide Web

  • ASCII-based HTTP (Hyper-Text Transfer Protocol) over TCP/IP

Summary

SaaS webapps are examples of client-server architectural pattern.

This is built upon the fundamentally client-server architecture of the Web.

Webapps use open standards, so that anyone can implement royalty-free, compared to some older client-server standards.

p2p (peer to peer) is an alternative, all entities act as both clients and servers.

The primary difference between the clients and servers:

  • client is optimized for user to interact with information
  • server is optimized for serving many clients simultaneously.

HTTP Routes: SaaS Communication

Network Protocol: A set of communication rules on which agents participating in a network agree.

TCP/IP (Transmission Control Protocal)

  • also called Internet Protocal
  • Fundamental protocal linking all computers on Internet.
  • Allows:
    • a pair of agents
    • to exchange ordered sequnces of bytes
    • in both directions
    • simultaneuously
  • This is called Full Duplex
    • Simplex: one direction only
    • Half Duplex: 2 directions, but one at a time
    • Full Duplex: 2 directions at the same time

TCP/IP Does not distinguish Server/Client in a connection, and does not have restrictions on the communication. It’s the individual program’s responsibility to determine the rules.

How communication works

Each computer is assigned an IP Address, 4 bytes separated by .

Domain Name System (DNS) is an Internet Service that

  • has its own protocol based on TCP/IP
  • map hostnames to IP addresses

A special IP Address is 127.0.0.1 which has an alias localhost. It refers to the computer that the app is running.

It provides an abstraction that the local machine works exactly the same as remote TCP/IP based server from the client’s perspecitve.

Port is introduced to distinguish different apps running on the same machine

  • range from 1 to 65535
  • Some program must listen to the port to accept connections.

HTTP Protocol

Rule for communication to make a request and receive a response.

  1. Client initiates a TCP/IP connection.
    • If the server doesn’t have a http server, then the client experiences an error. “Connection Refused / This site can’t be reached”
  2. Connection succeeds, the client immediately sends an HTTP request
    • describing its intention to perform some operation on a Resource
    • Resource: any entity that the server app manipulates. Can be a web page, image, form submission, etc.
  3. The server delivers an HTTP response that either satisfying the clients request or report any errors
    • may also include HTTP cookie that allows the server to identify the same client on future interactions.

Request and Response

HTTP Request:

  • HTTP Route
    • HTTP protocol version
    • HTTP Method: GET, POST, PUT, PATCH, DELETE
      • same URI, different methods means different requests
    • Uniform Resource Identifier (URI)
      • scheme: http, https
      • hostname
      • (port)
      • resource path
      • (query terms): key-value pairs
      • (fragment)
  • (zero or more) headers
  • (possibly) request body

HTTP Response

  • 3-digit status code on the first response
    • may have additional text information, but often for human readability, and would be ignored by the client
  • headers: describing the rest of the response data
  • response payload

HTTP is a request-response protocol, always starts with client’s request.

Cookies: Why and how

This is because HTTP is a stateless protocol, every request is independent and unrelated to previous requests.

So to keep track of information, HTTP provides a mechanism called cookies.

  • the first time a client makes a request to a particular server, the server can include in the header: Set-Cookie: xxx
  • it is the client’s responsibility to store the information and pass it back via Cookie: xxx header.

The coockie should be tamper-evident (防拆封的) and opaque (不透明) to the client. So it is sufficient to identify the client.

It simplifies server design, at the expense of more complex application design.

Summary

browsers and servers communicate using HTTP that relies on TCP/IP, that reliably exchange an ordered sequence of bytes

Computer are connected to a TCP/IP network through an IP address. DNS allows the use of a human-friendly name.

Each application running on a computer must listen on a distince TCP port.

URI names a resource available on the internet

HTTP route consists of both an HTTP methods and a URI

HTTP is a stateless protocol, every request is indepenent. HTTP cookies allow the association of HTTP requests form the same user.

Service Oriented Architecture: From Sites to Microservices

You start with a small trivial project, and you should never expect it to get large.

History

in 1990s, HTTPS servers were to serve static contents (like scientific papers) that a browser would display.

in 1995, SaaS emerges, and servers would now run a program and create HTML pages “on the fly”. But on each new HTTP request, the browser always load and display a new page.

Then AJAX (Asynchronous JavaScript And XML) appears, allow the page to include code written in js, which could make subsequent HTTP requests server without causing the page reload.

  • The server would return a data structure in JSON or XML, instead of an HTML.
  • The browser that runs the js code would determine how to change the appearance or behavior of the displayed page, without causing page reload.

The changes the relationship between a website and a client:

  • Past: receiving HTML pages and functioning primarily as a display engine
  • Then: client was essentially calling a funciton on the remote server and expecting to get some data back, like calling a library function.

This invited a new way of looking at the web:

  • a set of independent services that could be composed to produce latger sites.

This is called Servie Oriented Architecture (SOA)

Intro to SOA

SOA as an architectural pattern

Amazon.com

  • subsystem’s data and functionality would only be exposed through service interfaces
  • no subsystem allowed to access other subsystem’s data directly.
  • such interface must be designed so that someday it can be exposed to external developers.

This captures the critical distinction of SOA

  • the only way on service can name or access another service’s data is to request specific operations on that data through an external interface that provides those operations

Intro to Microservice

Microservice: is a standalone service that performs just one type of task, and is specifically designed to be accessible from and incorporated into the functionality of any other outside service.

There is no clear boundary separating microservice and service. The prefix “Micro” shows the stance of an “extreme SOA” design.

A rough rule of thumb of the scope:

  • correspond to a set of closely related operations on a very tightly integrated set of resources.

Pros and Cons

Pros:

Reusability

  • others can recombine services to create new apps.
  • each service can be implemented using the most appropriate language or framework

Easier Testing

  • does only one thing, so test is easier.

Agile-Friendly

  • Agile works best with small to medium projects and teams.
  • SOA allow large services to be created by composing smaller ones.

“You build it, you run it”

  • the same tightly knit team is responsible for developing, testing and operating.
  • So that a servce can be improved more quickly in response to customer requests

Cons:

Performance

  • invocation of a service involves higher cost of wading through the deeper software stack of a network interface

Managing partial failure

  • Monolithic system is either working or not
  • in SOA, some services may fail, while others are working
  • dependability and error handling more challenging.

More development work

  • must design and implement and interface for each service component, rather than a single interface
  • however, this can be simplified with an approach called REST.

Developers must learn more about operations, and Operators must know more about developing.

  • This is called dev/ops

Unix Philosophy

comes from the influence of the Unix operating system and its careful design choices.

Promotes the building of simple components that perform just one task and are easily composable.

The output from any component shoud constitute legal input to any other.

Summary

SOA means an approach to software development in which subsystem can only access each other’s data via external interfaces

Web 1.0 -> SaaS on AJAS -> SOA

there’s no bright line separating a service from a microservice.

A microservice should

  • perform a related set of operations on a well circumscribed set of resources
  • should be independently deployed and operated
  • should be designed to be readily incorporated with other external services

Reuse is the mechanism that SOA best exemplify among

  • Clarity via conciseness
  • Synthesis
  • Reuse
  • Automation and Tools
    Because the purpose of making internal interfaces visible is for other programmers to reuse.

RESTful APIs: Everything is a Resource

We can consider the interface or operations of a app as an analogy of some library for a programming language.

So, we need a way or a set of rules

  • name the server functions
  • pass arguments to them
  • consume their return values
  • detect and handle exceptions

The term Application Programming Interface (API) refers to the “contract” between a caller and a callee.

Comparison: libraries and SaaS interfaces

How does caller identigy the callee

  • Library: same computer and same process, use key word like import
  • SaaS: endpoint as a logical address that clients contact to use the service. It could be a “base URI” or “URI prefix”

Which operation is called

  • Library: Method named in code.
  • SaaS Operation named n path portion of URI

How does the caller pass required and optional params to the callee

  • Library: args to method call
  • SaaS: may be part of URI path, key value pairs in query string, or as data payload

How does the caller receive a return value

  • Library: from method call.
  • SaaS: a data structure returned by Service

How does the callee signal an error:

  • Library: callee may return a sentinel error value or raise exception
  • SaaS: return an appropriate HTTP status code.

RESTful API

Background:

However, HTTP doesn’t provoide the feature like “remote function name” or “pass parameters”. This is because the HTTP and URI specifications offer no conventions regarding the semantics of how URI are constructed.

Motivation:
By standardizing the conventions, it would enable the creation of an ecosystem in which any client can make use of a given server.

This convention is invented as REpresentational State Transfer (REST).

REST is not standard, but a design stance that describes how a service should be constructed, and what its API should look like.

Representational

  • Various entities manipulated by a webapp are regarded as Resources

State Transfer

  • Construct routes so that any HTTP request would contain all the information necessary to identify both a resource and the action to be performed.
  • This may cause a change of state in one or more resources

An API that adheres to this guideline is called RESTful. And the routes defined by the API are called RESTful routes.

Questions to be answered by APIs

  • What is the primary resource affected by the operation
  • What is the operation to be done on that resource? What are the possible results? What are the possible side effects?
  • What other data is necessary to complete the operation? How is it specified?

CRUDI: Five Operations

Simplest RESTful API defines up to five operations on a resource, captured by the acronym CRUDI

  • Create
  • Read / Retrieve
  • Update
  • Delete
  • Index

Many APIs go further and define additional operations.

Each Resource is almost always has its unique ID. A common usage pattern is to return a list of resources with their IDs corresponding to a search operation. The client can then retrieve the desired resources one by one via their IDs.

Actions having no side effects typically use GET. Those with side effects use POST, PUT or PATCH.

API Documentation

API Documentation describes

  • what operations are available
  • how the required and optional arguments should be provided

Hostnam component of the URI: Which server provdes the service.

  • Most servers specify a base URI or common URI prefix like https://api.themoviedb.org/4/
    • Such base URI is sometimes referred to as the API endpoint, or logical address.
    • the 4 refers to the version number of the API, which allows the API to evolve while preserving compatibility with older clients.
  • the following path components specifies the operation to be performed and the resource on which to perform it.
    • in the documentaion, we often use a colon : or curly braces to indicate a URI component
    • GET /movie/{movie_id} GET /movie/:movie_id
  • Some URI structures itself suggests the relationship between resources, like GET /movies/5/reviews/22

Command Query Separation

A given method or operation should either be data-altering (command) or read-only (query) but not both.

REST respects this principle and futher separates the responsibilities of different operations.

Summary

To treat SaaS apps as services and remote procedure calls, we need to be able to identify the service and which operation is to be called, pass data and receive data, handle errors.

REST is a simple, consistent way to regulate HTTP routes and API operations

The key idea of REST is to represent entities managed by the service as resources, and provide a limited set of operations on the resource.

RESTful URIs, API Calls and JSON

How data is passed to or received from the SOA services? How are authorization and errors handled?

Different ways to pass data:

  • URI path to
  • arguments in URI
  • payload

JSON JavaScript Object Notation

HTTP headers are sometimes used to pass specialized types of parameters.

  • Content-Type: application/json refers to a request that will be accompanied by a JSON payload.

Error handling

2xx: success.
3xx: the client must take further action to complete the request: redirect.
4xx: the service encountered an application error processing the request.
- 400: the request was malformed.
- 401: unauthorized
- 402: payment required
5xx: a problem with the service infrasture itself. nothing can be done from the client side.

Alternatives of REST

There are also other conventions and standards.

  • SOAP, WSDL, UDDI, XML-RPC, DCOM, Jini, CORBA

The REST wins because

  • it is easier for developers to understand and use
  • it is matched to the underlying technology stack
  • not subject to a costly or restrictive license

Pitfalls

Fallacy: Splitting a large “monolithicl” service into microservices decreases complexity

  • The system complexity does not disappear, but distributed among the microservices, and how these services are managed.
  • The 2 main structural patterns for coordination among microservices are
    • orchestration: the composition layer has a higher level of complexity and hold more of the application’s logic
    • choreography: the services interact among themselves without a separate composition layer.
  • Splitting Large service also requires thinking about the boundaries.

Fallacy: Publishing my API makes my service RESTful

  • publishing just means external calles are allowed.

Fallacy: I havn’t published an API, so clients cannot call my app.

  • The clients can extract information from a regular HTTP Request, and then extract information from the HTML page.

Pitfall: Thinking in terms of URIs, user actions, views, instead of thinking in terms of resources.

  • We would assume a normal sequence of operations to make some functionalities work, and ignore the unexpected behaviors.
  • To avoid this, we need to think in terms of the resources.

Pitfall: Poor design of API resulting from misunderstanding of the domain or of the customers’ use cases

  • it leads to inefficient resource representation internally. But it does not necessarily leak into API.
